# キー位置の送信（raw HID）

キーが押された／離されたときに、その**位置番号**と**押した／離した**を、PC のアプリ（桜雪など）に送る仕組みです。
ファームウェアの実装は [lalapad/src/key_stream.c](../lalapad/src/key_stream.c)（送り道は `key_stream_usb.c`・`key_stream_ble.c`）。
確認用のページは [docs/tools/key-stream-viewer.html](tools/key-stream-viewer.html) です（Chrome か Edge で開くだけで使えます）。

## しくみ

- 左（親機）が、左右のキーをまとめて送ります。右のキーも、親機には同じ位置番号の出来事として届くので、PC 側で左右を気にする必要はありません。
- **ベンダー定義の HID（raw HID）**を、ふだんのキーボードの HID とは別にもう1つ出しています。
  - USB：HID の機器をもう1つ増やしています（`HID_1`）。
  - Bluetooth：HID のサービス（HID over GATT）をもう1つ増やしています。
  - どちらも、PC からは同じ raw HID に見えるので、**WebHID でそのまま読めます**。
- 送るのは、アプリから**「開始」を受けている間だけ**です。アプリは開いている間、2 秒ごとに「開始」を送り直してください（生存確認）。6 秒届かなければ、キーボードは送るのをやめます。
- 送る先は、最後に「開始」が届いた送り道（USB、または Bluetooth のその接続）です。
- ただし、**キーボードがいまキーの入力を送っている PC からの「開始」だけ**を受け付けます（下の「送る相手」）。
- どの文字が出たかは送りません。今有効なレイヤーは、「開始」で頼んだときだけ送ります（下の `0x04`）。

## 送る相手

別の PC で打った内容が、ほかの PC のアプリに見えないように、キーボードがいまキーの入力を送っている PC（入力先）にだけ送ります。

- 入力先は ZMK が選んでいる送り道です。USB と Bluetooth の両方がつながっているときは、`&out` で選んだほう（`OUT_USB`／`OUT_BLE`）です。Bluetooth のときは、`&bt` で選んでいるプロファイルの PC だけが入力先です（ほかのプロファイルでつながったままの PC は入力先ではありません）。
- 入力先でない PC からの「開始」は、**黙って無視します**（何も答えません）。USB でつないでいても、入力先が Bluetooth なら受け付けません（逆も同じ）。問い合わせ（`0x83`）・終了（`0x82`）も、今送っている相手からのものだけを扱います。
- 送っている間に入力先が変わったら（`&out` での USB ⇔ Bluetooth の切り替え、`&bt` でのプロファイルの切り替え、USB を抜き差ししたときの自動の切り替えなど）、その時点で送るのをやめます。やめたことは知らせません（最後のレポートの後、何も届かなくなります）。送り待ちだったキーは捨てます。
- アプリは、届かなくても**「開始」を 2 秒ごとに送り続けてください**。入力先がその PC に戻ると、次の「開始」で始め直しとして、状態（`0x02`）・押されたままのキー・押されているキーの一覧（`0x03`）から送り直します（最大で生存確認 1 回分、2 秒ほど遅れます）。止まっている間に押したり離したりしたキーは届きませんが、一覧で直ります。
- 送り待ちだったキーを捨てた分は、始め直したときの状態（`0x02`）の通し番号が飛んで見えます（取りこぼしと同じ扱い）。止まっている間のキーには番号を振らないので、その分は飛びません。
- アプリからは、入力先でないために届かないのか、キーを打っていないだけなのかは、届くものだけでは区別できません。確かめたいときは問い合わせ（`0x83`）を送ってください。送っている間は状態と一覧が届き、送っていない（入力先ではない）ときは何も届きません。

## 見分けるための値

| 項目 | 値 |
| --- | --- |
| VID / PID | `0x1D50` / `0x615E`（ZMK の標準。USB・Bluetooth とも同じ。**ほかの ZMK キーボードとも同じ**） |
| usage page / usage | `0xFF4C` / `0x01` |
| 製品名 | `LalapadGen2` |
| レポート | 入力・出力とも **32 バイト**、レポート ID なし（WebHID では `reportId` 0） |

VID/PID はほかの ZMK キーボードと同じなので、usage page と製品名も合わせて見分けてください。

## レポートの形

どのレポートも、先頭の 2 バイトは共通です。足りない分は 0 で埋めます。数値は**リトルエンディアン**です。

| 位置 | 中身 |
| --- | --- |
| 0 | 形式の版（今は `1`） |
| 1 | 種類 |
| 2 以降 | 種類ごとの中身 |

知らない種類は読み飛ばしてください（あとで種類を足しても、組み合わせられるように）。

### キーボード → アプリ

**`0x01` キー**（押した・離したが、1 件から 4 件まとめて届く）

| 位置 | 中身 |
| --- | --- |
| 2〜3 | 先頭の通し番号（u16） |
| 4 | 件数 n（1〜4） |
| 5 + 6×i | 位置番号（0〜67） |
| 6 + 6×i | 印：bit0 = 押した（1）／離した（0）、bit1 = 「開始」したときに押されたままだったキー |
| 7 + 6×i 〜 10 + 6×i | 時刻（キーボードが起動してからのミリ秒、u32） |

- 通し番号は 1 件ごとに 1 つ進みます。前のレポートから飛んでいたら、その分を取りこぼしています（送り切れずにたまりすぎたとき、送り終わらないレポートを見切ったとき）。そのときは、送り待ちを送り終えた後に、押されているキーの一覧（`0x03`）が届きます。
- 通し番号は 65535 の次が 0 に戻ります。差は 65536 で割った余りで見てください。差が `0x8000` 以上（前より戻っている）なら、キーボードが再起動したなどで番号が振り直されています。取りこぼしとは数えずに、届いた番号から数え直してください。ただし、これは目安です（再起動の後の番号が、たまたま前より進んで見えることもあります）。機器を開いたとき・つなぎ直したときは、前の番号を引き継がず、その後に最初に届いたレポートの番号から数え始めてください。
- 時刻はキーボード側の時計です。Bluetooth では数件まとめて届くことがあるので、打鍵の間隔はこちらで見てください。

**`0x02` 状態**（「開始」したとき、右のつながりが変わったとき、問い合わせたとき、送り終わらなかった状態を送り直すときに届く）

| 位置 | 中身 |
| --- | --- |
| 2 | 右との Bluetooth の接続がある（1）／ない（0）。1 でも、つながった直後などは、右のキーがまだ届かないことがあります |
| 3 | 今送っている種類（「開始」で指定したもの） |
| 4 | キーの位置の数（この番号より前がキー。今は 52） |
| 5 | 位置の数の合計（今は 68） |
| 6〜7 | 次に送るキーの通し番号（u16） |
| 8 | できること（bit0 = 書き込み待ちの命令 `0x84`・`0x85` を受け付ける。キーマップに `&bootloader` があるときだけ 1。bit1 = レイヤーの見分けの番号の問い合わせ `0x86` に番号を答える。キーマップのレイヤーに `layer_id_<番号>:` のラベルを付けているときだけ 1） |

- 6〜7 の番号も、キーと同じように前のキーの続きと比べてください。飛んでいたら、その分を取りこぼしています（送り切れずに捨てた分や、送るのをやめたとき・種類を変えて「開始」し直したときに送らずに捨てた分）。

**`0x03` 押されているキーの一覧**（「開始」したとき、問い合わせたとき、キーを取りこぼしたときに届く）

| 位置 | 中身 |
| --- | --- |
| 2〜3 | 通し番号（u16）。この番号より前のキーまでを反映した一覧 |
| 4 | 位置の数の合計（今は 68） |
| 5〜13 | 押されている位置のビット。位置 p は、5 + p÷8（切り捨て）バイト目の bit (p％8)。1 = 押されている |

- 届いたら、表示などの「押されている」状態を、この一覧で**丸ごと置き換えて**ください。0 の位置は離されています。取りこぼした「離した」も、これで直ります。
- 今送っている種類の位置だけが入ります（トラックパッドを受け取っていなければ、52〜67 は 0）。
- キーの列の順番どおりに届きます（それより前のキーを送り終えてから、その時点の状態を送ります）。2〜3 の番号は、前のキーの続き（次に来るはずの番号）と同じになります。飛んでいたら、その分を取りこぼしています。この後に届くキーは、この番号から続きます。
- 送り待ちがあふれてキーを捨てたときは、問い合わせなくても、送り待ちを送り終えた後に届きます。

**`0x04` レイヤー**（「開始」でレイヤー（bit2）を頼んだときだけ。「開始」したとき、問い合わせたとき、レイヤー・修飾キーが変わったときに届く）

| 位置 | 中身 |
| --- | --- |
| 2〜5 | 有効なレイヤー（u32）。レイヤー ID ごとのビット（bit L = レイヤー L が有効）。Default と条件付きレイヤーも含む |
| 6 | レイヤーの数 |
| 7〜10 | このレポートを作った時刻（キーボードが起動してからのミリ秒、u32） |
| 11 | 押している修飾キー（bit0 左 Ctrl、bit1 左 Shift、bit2 左 Alt、bit3 左 GUI、bit4〜7 右の同じ順。HID の修飾キーと同じ並び） |
| 12 | 有効なレイヤーの件数 n（1〜19。この欄のない古いファームウェアでは 0） |
| 13 〜 12 + n | 有効なレイヤーの ID。ZMK がキーを探す順（いちばん上から、いちばん下の Default まで） |

- レイヤー ID は、キーマップに書いた順番（0 から）です。ZMK Studio でレイヤーの順番を入れ替えても ID は変わりません。
- レイヤーの上下は、13 以降の並びで見てください（先頭がいちばん上）。ZMK Studio でレイヤーの順番を入れ替えていても、ZMK がキーを探す順番どおりに並びます。
  透過（`&trans`）のキーは、この並びの次のレイヤーの割り当てになります。有効なレイヤーが 20 個以上あるときは、上の 19 個だけが入ります（残りは 2〜5 のビットで分かります）。
  12 が 0 の古いファームウェアでは、いちばん大きいビットがいちばん上です（Studio で順番を入れ替えていると合いません）。
- キーで変わったもののほか、トラックパッドを動かしたときのオートマウスレイヤー、Num Word、かなモード、レイヤーの固定など、どの仕組みで変わっても届きます。
- 送るのは作った時点の状態です。続けて何度も変わったときは、まとめて最後の状態だけが届くことがあります。キー（`0x01`）より先に送るので、レイヤーを変えたキーより先に届くことがあります。
- 送り終わらないまま見切ったときは、もう一度送ります（そのときの状態）。
- 修飾キーは、修飾キーそのものを押しているもの（`&kp LSHIFT`、`&mt` の長押しの Shift、`&sk LSHIFT` など）だけです。`LS(N1)` のようにキーに付いた修飾キーは含みません（アプリで「Shift を押している間は Shift 面を出す」ために使えます）。
- 修飾キーは、キーを押している間と修飾キーが残っている間、20ms ごとにも見直して、変わっていれば送ります（長押しの判定の間に押し離しした修飾キーなど、知らせが届かない変化のため）。

**`0x05` 書き込み待ちの答え**（`0x84`・`0x85` を受けたときに届く）

| 位置 | 中身 |
| --- | --- |
| 2 | どちら（0 = 親機（左）、1 = 子機（右）） |
| 3 | 結果（0 = 書き込み待ちにする、1 = 準備した、2 = 準備していない・3 秒を過ぎた・どちらが違う・もう入ると決めた、3 = 子機とつながっていない、4 = できない（`&bootloader` がない）） |

- 結果が 0 のとき、入ると決めてから 0.5 秒後に、書き込み待ち（UF2 のブートローダー）に入ります。答えは届けるよう努めますが、届かないこともあります
  （届いたかどうかとは結びつけません）。アプリは、答えが来なくても、書き込み待ちのドライブが出たら入ったとみなしてください。
  入ると決めてから入るまでの間は、ほかの書き込み待ちの命令を受け付けません（結果 2）。USB でつないでいれば、PC にドライブが出ます。子機には、親機から分割の仕組みで伝えます。
- 答えは送り直しません。届かなければ、アプリは時間で見切ってください。

**`0x06` レイヤーの見分けの番号**（`0x86` を受けたときに届く）

| 位置 | 中身 |
| --- | --- |
| 2 | このレポートの先頭のレイヤー ID |
| 3 | レイヤーの数（番号がないファームウェアでは 0） |
| 4 | このレポートの件数 n（0〜27） |
| 5 〜 4 + n | レイヤー ID ごとの見分けの番号（1〜255）。5 + i バイト目が、レイヤー ID（先頭 + i）の番号 |

- 見分けの番号は、キーマップのレイヤーのノードに付けたラベル（`layer_id_7: KANA_LAYER { … }` の 7）です。
  レイヤーを作ったときに決め、名前を変えても並べ替えても変えません（ラベルは、全部のレイヤーに付けるか、1 つも付けないか）。アプリは、キーボードのレイヤー ID（`0x04` のビット）を、
  この番号でキーマップのファイルのレイヤーに対応させてください（書き込んでいない並べ替え・追加があっても、同じレイヤーを指せます）。
- レイヤーの数が 27 を超えるときは、続きが次のレポートで届きます（2 の先頭のレイヤー ID で並べてください）。
- 送り終わらないまま見切ったときは、先頭から送り直します。
- レイヤーにラベルを付けていないファームウェアは、レイヤーの数 0 のレポートを 1 つ返します（`0x02` の 8 の bit1 も 0）。
  そのときは、レイヤー ID をキーマップのファイルの順番と同じとみなしてください。`0x86` を知らない古いファームウェアは何も答えません。

### アプリ → キーボード

| 種類 | 名前 | 中身 |
| --- | --- | --- |
| `0x81` | 開始・生存確認 | 位置 2：送ってほしい種類（bit0 = キー 0〜51、bit1 = トラックパッドのタップ・ジェスチャー 52〜67、bit2 = レイヤー `0x04`） |
| `0x82` | 終了 | なし |
| `0x83` | 状態の問い合わせ | なし（送っている間だけ答える。状態 `0x02` と、押されているキーの一覧 `0x03`、レイヤーを頼んでいればレイヤー `0x04` を送る） |
| `0x84` | 書き込み待ちの準備 | 位置 2：どちら（0 = 親機（左）、1 = 子機（右））。3 秒の間だけ、次の `0x85` を受け付ける |
| `0x85` | 書き込み待ちにする | 位置 2：どちら（`0x84` と同じ） |
| `0x86` | レイヤーの見分けの番号の問い合わせ | なし（送っている間だけ答える。答えは `0x06`） |

- 「開始」が届くと、すぐに状態（`0x02`）、レイヤーを頼んでいればレイヤー（`0x04`）、その時点で押されたままのキー（`0x01`。印の bit1 が 1）、押されているキーの一覧（`0x03`）の順に送ります。押されたままのキーは、`0x01` と `0x03` のどちらで受け取ってもかまいません。
- 同じ送り道・同じ種類の「開始」は、生存確認として扱います（状態は送り直しません）。種類を変えて「開始」を送ると、始め直しとして、状態と押されたままのキーを送り直します。このとき、まだ送っていなかったキーは捨てます（通し番号はその分も進んでいるので、番号が飛んで見えます。押されているキーは、続けて届く一覧で直ります）。押されたままのキーだけを送り直してほしいときは、問い合わせ（`0x83`）を送ってください。始め直す前に送り始めていたものは、始め直しの状態（`0x02`）より先に届くことがあります（次の `0x02` までに届くものは、前の種類で作られています）。
- 入力先でない PC からの「開始」は無視します（何も届きません。上の「送る相手」）。
- 書き込み待ち（`0x84`・`0x85`）は、送っている相手（入力先の PC で「開始」を送り続けているアプリ）からのものだけを受け付けます。
  うっかり入らないよう、準備（`0x84`）の後 3 秒以内に、同じ送り先・同じ「開始」のままで、同じどちらへの実行（`0x85`）が来たときだけ入ります
  （準備は 1 回で使い切る。止めたり始め直したりすると消える）。入力先が変わった直後（照合の前）は受け付けません。
  これは誤操作を防ぐためのもので、相手のアプリを確かめるものではありません（入力先の PC で、この HID を開けるアプリなら送れます）。
  親機は自分で、子機には親機から「子機の `&bootloader` のキーを押した」ことにして伝えます（子機のファームウェアは変えない。子機にも同じキーマップが入るため、
  キーマップに `&bootloader` があれば動きます）。書き込み待ちの間はキーボードとして使えません。ドライブに `.uf2` を写すか、リセットを押すと戻ります。
- 両方を書き込むときは、子機（右）を先に、親機（左）を後にしてください（親機が先に書き込み待ちになると、子機へ伝えられないため）。
- アプリを開いたときは、最初の「開始」の後に問い合わせ（`0x83`）も送ってください。アプリを閉じてから 6 秒たつ前に開き直すと、キーボードはまだ前の「開始」で送り続けているので、今の「開始」は生存確認として扱われ、状態と押されているキーが届きません。
- 右が切れたときは、状態（右＝切れている）と、右で押されていたキー（0〜51 のうち右手側）の「離した」が届きます。どちらが先に届くかは決まっていません（状態は送り待ちのキーより先に送るため）。右のトラックパッドのタップ・ジェスチャーの位置（55〜57、63〜67）は、ZMK が「離した」を出さないので、押されたまま切れたものは、キーボードが切れたのに気づいた時点で自分で離し、その「離した」が届きます（トラックパッドを受け取っているときだけ。時刻は気づいた時刻）。
- 位置番号の並びは [README の「キーの位置番号」](../README.md#キーの位置番号) を見てください。

### 例（WebHID）

```js
const [device] = await navigator.hid.requestDevice({
  filters: [{ vendorId: 0x1D50, productId: 0x615E, usagePage: 0xFF4C, usage: 0x01 }],
});
await device.open();
device.addEventListener('inputreport', (e) => { /* e.data（DataView）を上の表のとおりに読む */ });
const start = new Uint8Array(32); start[0] = 1; start[1] = 0x81; start[2] = 0x01;
await device.sendReport(0, start);
const query = new Uint8Array(32); query[0] = 1; query[1] = 0x83;
await device.sendReport(0, query); // 今の状態と押されているキーを受け取る（開き直したときのため）
setInterval(() => device.sendReport(0, start), 2000); // 生存確認
```

## キーの実際の配置

キーの実際の配置（カラムスタッガード、親指キーの大きさなど）は [docs/key-stream-layout.json](key-stream-layout.json) にあります（0〜51。トラックパッドの位置は含みません）。

- 単位は u（1u = キーピッチ 19mm）。x は右、y は下が正です。`x`・`y` は回転前のキーの左上、`w`・`h` は幅と高さ、`r` はキーの中心まわりの回転（度、時計回りが正）です。親指キーは、33（右は 38）は傾けず、34・35（右は 37・36）を下の辺をつなげて 7° ずつ扇形に傾けています。
- 5 方向スイッチは、中心と上下左右を 0.2u の小さなキーとして表しています。
- 右手は左手を左右反転した形です。左右の間隔は、左右を並べて置いた写真に合わせています（実際の置き方で変わるので、必要ならアプリ側で調整してください）。
- 真上から撮った実機の写真から測った近似です。0.1u ほどずれていることがあります。
- ファームウェアでは使っていません（キーマップのエディタ用の配置は、編集しやすいよう碁盤の目のままです）。

## ふだんの入力への影響

- キーの出来事は見るだけで、止めたり変えたりしません。送る処理は専用のスレッドで行います。
- 送るのは 1 つずつ（送り終わってから次）で、Bluetooth の送信の空きは文字の入力のほうに残します。送り切れないほどたまったら、古いものから捨てます（通し番号で分かります）。
- 送り終わらないレポート（USB のリセットなど）は、USB は 0.5 秒、Bluetooth は 3 秒で見切って次へ進みます。見切ったものは届かないことがあるので、その後に押されているキーの一覧（状態を見切ったときは状態）を送り直します。
- 送れない状態（USB のサスペンド中など）が 5 秒続いたら、送るのをやめます。アプリが「開始」を送り続けていれば、次の「開始」でまた始まります（状態と押されているキーから送り直します）。
- 「開始」を受けていない間は何も送らないので、電池にも響きません。

## 注意

- 書き込んだ後、Windows が Bluetooth のキーボードの情報を古いまま覚えていると、増えた HID が見えないことがあります。そのときは、Windows の Bluetooth 設定でキーボードを削除して、ペアリングし直してください。
- Bluetooth では、ATT MTU が 35 以上でないと使えません（32 バイトのレポートに頭 3 バイトが付くため）。MTU が小さい（23 のまま）ときは、アプリからの 32 バイトの「開始」もキーボードに届かないので、送り始めません（Windows はふつう MTU を広げるので、この状態にはなりません）。また、「開始」は暗号化した（ペアリング済みの）接続でしか受け付けません。
- 書き込むのは左だけです（右は変わりません）。
- 止めたいときは、`config/lalapadgen2_left.conf` の `CONFIG_ZMK_KEY_STREAM=y` と `CONFIG_USB_HID_DEVICE_COUNT=2` の両方を消します（HID の数を 2 のままにすると、使わない HID が USB に残ります）。Bluetooth 側だけ止めるなら `CONFIG_ZMK_KEY_STREAM_BLE=n` を足します。
