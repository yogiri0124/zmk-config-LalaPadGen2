# キー位置の送信（raw HID）

キーが押された／離されたときに、その**位置番号**と**押した／離した**を、PC のアプリ（桜雪など）に送る仕組みです。
ファームウェアの実装は [lalapad/src/key_stream.c](../lalapad/src/key_stream.c)（送り道は `key_stream_usb.c`・`key_stream_ble.c`）。
確認用のページは [docs/tools/key-stream-viewer.html](tools/key-stream-viewer.html) です（Chrome か Edge で開くだけで使えます）。

## しくみ

- 左（親機）が、左右のキーをまとめて送ります。右のキーも、親機には同じ位置番号の出来事として届くので、PC 側で左右を気にする必要はありません。
- **ベンダー定義の HID（raw HID）**を、ふだんのキーボードの HID とは別にもう1つ出しています。
  - USB：HID の機器をもう1つ増やしています（`HID_1`）。
  - Bluetooth：HID のサービス（HID over GATT）をもう1つ増やしています。
  - どちらも、PC からは同じ raw HID に見えるので、**WebHID でそのまま読めます**。
- 送るのは、アプリから**「開始」を受けている間だけ**です。アプリは開いている間、2 秒ごとに「開始」を送り直してください（生存確認）。6 秒届かなければ、キーボードは送るのをやめます。
- 送る先は、最後に「開始」が届いた送り道（USB、または Bluetooth のその接続）です。
- どの文字が出たか・どのレイヤーかは、今は送りません（あとで種類を足せる形にしてあります）。

## 見分けるための値

| 項目 | 値 |
| --- | --- |
| VID / PID | `0x1D50` / `0x615E`（ZMK の標準。USB・Bluetooth とも同じ。**ほかの ZMK キーボードとも同じ**） |
| usage page / usage | `0xFF4C` / `0x01` |
| 製品名 | `LalapadGen2` |
| レポート | 入力・出力とも **32 バイト**、レポート ID なし（WebHID では `reportId` 0） |

VID/PID はほかの ZMK キーボードと同じなので、usage page と製品名も合わせて見分けてください。
usage page と usage は `config/lalapadgen2_left.conf` の `CONFIG_ZMK_KEY_STREAM_USAGE_PAGE`・`CONFIG_ZMK_KEY_STREAM_USAGE` で変えられます。

## レポートの形

どのレポートも、先頭の 2 バイトは共通です。足りない分は 0 で埋めます。数値は**リトルエンディアン**です。

| 位置 | 中身 |
| --- | --- |
| 0 | 形式の版（今は `1`） |
| 1 | 種類 |
| 2 以降 | 種類ごとの中身 |

知らない種類は読み飛ばしてください（あとで種類を足しても、組み合わせられるように）。

### キーボード → アプリ

**`0x01` キー**（押した・離したが、1 件から 4 件まとめて届く）

| 位置 | 中身 |
| --- | --- |
| 2〜3 | 先頭の通し番号（u16） |
| 4 | 件数 n（1〜4） |
| 5 + 6×i | 位置番号（0〜67） |
| 6 + 6×i | 印：bit0 = 押した（1）／離した（0）、bit1 = 「開始」したときに押されたままだったキー |
| 7 + 6×i 〜 10 + 6×i | 時刻（キーボードが起動してからのミリ秒、u32） |

- 通し番号は 1 件ごとに 1 つ進みます。前のレポートから飛んでいたら、その分を取りこぼしています（送り切れずにたまりすぎたとき）。
- 時刻はキーボード側の時計です。Bluetooth では数件まとめて届くことがあるので、打鍵の間隔はこちらで見てください。

**`0x02` 状態**（「開始」したとき、右のつながりが変わったとき、問い合わせたときに届く）

| 位置 | 中身 |
| --- | --- |
| 2 | 右がつながっている（1）／切れている（0） |
| 3 | 今送っている種類（「開始」で指定したもの） |
| 4 | キーの位置の数（この番号より前がキー。今は 52） |
| 5 | 位置の数の合計（今は 68） |
| 6〜7 | 次に送るキーの通し番号（u16） |

- 6〜7 の番号も、キーと同じように前のキーの続きと比べてください。飛んでいたら、その分を取りこぼしています（送り切れずに捨てた分や、送るのをやめたときに送らずに捨てた分）。

### アプリ → キーボード

| 種類 | 名前 | 中身 |
| --- | --- | --- |
| `0x81` | 開始・生存確認 | 位置 2：送ってほしい種類（bit0 = キー 0〜51、bit1 = トラックパッドのタップ・ジェスチャー 52〜67） |
| `0x82` | 終了 | なし |
| `0x83` | 状態の問い合わせ | なし（送っている間だけ答える） |

- 「開始」が届くと、すぐに状態（`0x02`）と、その時点で押されたままのキー（`0x01`。印の bit1 が 1）を送ります。
- 同じ送り道・同じ種類の「開始」は、生存確認として扱います（状態は送り直しません）。種類を変えて「開始」を送ると、状態と押されたままのキーを送り直します。
- 位置番号の並びは [README の「キーの位置番号」](../README.md#キーの位置番号) を見てください。

### 例（WebHID）

```js
const [device] = await navigator.hid.requestDevice({
  filters: [{ vendorId: 0x1D50, productId: 0x615E, usagePage: 0xFF4C, usage: 0x01 }],
});
await device.open();
device.addEventListener('inputreport', (e) => { /* e.data（DataView）を上の表のとおりに読む */ });
const start = new Uint8Array(32); start[0] = 1; start[1] = 0x81; start[2] = 0x01;
await device.sendReport(0, start);
setInterval(() => device.sendReport(0, start), 2000); // 生存確認
```

## ふだんの入力への影響

- キーの出来事は見るだけで、止めたり変えたりしません。送る処理は専用のスレッドで行います。
- 送るのは 1 つずつ（送り終わってから次）で、Bluetooth の送信の空きは文字の入力のほうに残します。送り切れないほどたまったら、古いものから捨てます（通し番号で分かります）。
- 「開始」を受けていない間は何も送らないので、電池にも響きません。

## 注意

- 書き込んだ後、Windows が Bluetooth のキーボードの情報を古いまま覚えていると、増えた HID が見えないことがあります。そのときは、Windows の Bluetooth 設定でキーボードを削除して、ペアリングし直してください。
- 書き込むのは左だけです（右は変わりません）。
- 止めたいときは、`config/lalapadgen2_left.conf` の `CONFIG_ZMK_KEY_STREAM=y` を消します。Bluetooth 側だけ止めるなら `CONFIG_ZMK_KEY_STREAM_BLE=n` を足します。
