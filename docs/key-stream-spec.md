# キー位置の送信（key stream）仕様書

キーボードが PC のアプリに「どのキーを押した／離したか」を送る仕組みの仕様。
この文書だけで、キーボード側（ファームウェア）とアプリ側の両方を作れるように、決まりごととその理由を書く。

- 対象の版: 形式の版（レポートの 0 バイト目）= **1**
- 元の実装（正）: [lalapad/src/key_stream.c](../lalapad/src/key_stream.c)（本体）、[key_stream_usb.c](../lalapad/src/key_stream_usb.c)（USB）、
  [key_stream_ble.c](../lalapad/src/key_stream_ble.c)（Bluetooth）、[key_stream.h](../lalapad/src/key_stream.h)（本体と送り道の取り決め）。ZMK v0.3.0（Zephyr 3.5）。
- 受け取る側の手本: [docs/tools/key-stream-viewer.html](tools/key-stream-viewer.html)（WebHID。キー・状態・一覧だけを扱う最小の実装）
- アプリを作る人向けの説明: [docs/key-stream.md](key-stream.md)（この文書と同じ内容を、使う側から書いたもの。LaLapad Gen2 に固有の値も入っている）
- この文書と元の実装が食い違うときは、元の実装が正しい（この文書を直す）。

## 1. 何をするものか

- キーボードは、キーの**位置番号**（キーマップでのキーの番号。0 から）と**押した／離した**と**時刻**を、PC のアプリに送る。
  どの文字が出たか（キーコード）は送らない。位置番号がどのキーかは、アプリがキーボードごとの資料（位置番号の並び）で決める。
- 通り道は、ふだんのキーボードの HID とは別の、**ベンダー定義の HID（raw HID）**。USB でも Bluetooth（HID over GATT）でも、PC からは
  同じ HID の機器に見えるので、アプリは **WebHID**（ブラウザ）や hidapi などで、つなぎ方を気にせずに読める。
- 送るのは、アプリが「開始」を送り続けている間だけ（生存確認）。アプリがいなければ何も送らない。
- 分割キーボードでは、PC とつながる側（親機）がまとめて送る。子機のキーも、親機には同じ位置番号の出来事として届くので、アプリは左右を区別しなくてよい。
- 拡張として、今有効なレイヤーと押している修飾キー（`0x04`）、書き込み待ち（ブートローダー）に入れる命令（`0x84`・`0x85`）、
  レイヤーの見分けの番号（`0x86`・`0x06`）がある。これらはなくても、キーの送信（`0x01`〜`0x03`、`0x81`〜`0x83`）だけで成り立つ。

```
 キーボード（親機）                                         PC のアプリ
 ───────────────                                         ───────────
 キーの出来事 ──見るだけ──▶ 送り待ち（輪状 64 件）              
                              │                         ◀── 0x81 開始（2 秒ごと。生存確認）
                              ▼                         ◀── 0x83 問い合わせ / 0x82 終了
                 専用スレッドが 1 つずつ送る ──raw HID──▶  0x02 状態 → 0x03 一覧 → 0x01 キー …
                 （送り終わりを待ってから次）
```

## 2. 守るべき設計の原則

移すときも、次の原則は変えないこと（どれも実際の問題から決めたもの）。

1. **ふだんの入力を邪魔しない。** キーの出来事は見るだけで、止めたり、遅らせたり、変えたりしない。送る処理は専用のスレッド（またはそれに当たるもの）で行う。
   送るのは常に 1 つずつ（前のレポートが送り終わってから次）。Bluetooth の送信の空きを、文字の入力のほうに残すため。
2. **頼まれている間だけ送る。** OS は HID を常に読んでいるので、キーボードからはアプリが開いているか分からない。アプリが 2 秒ごとに「開始」を送り、
   6 秒届かなければ送るのをやめる。送っていない間は何もしない（電池にも響かない）。
3. **入力先の PC にだけ送る（覗き見を防ぐ）。** キーボードが今キーの入力を送っている PC（USB か、Bluetooth のどのプロファイルか）からの「開始」だけを受け付け、
   ほかの PC からのものは**黙って無視する**（答えない）。送っている間に入力先が変わったら、その時点でやめる。別の PC で打った内容が、ほかの PC のアプリに見えないように。
4. **取りこぼしは、通し番号で分かるようにし、一覧で直せるようにする。** キーの 1 件ごとに通し番号（u16）を振る。送り切れずに捨てたら番号が飛ぶ。
   捨てたときは、押されているキーの一覧（`0x03`）を送り、アプリはそれで「押されている」状態を丸ごと置き換える（取りこぼした「離した」も直る）。
5. **順番を守る。** 一覧は、それより前のキーを送り終えてから、その時点の状態で送る。一覧の通し番号は「次に来るはずの番号」と同じになる。
6. **知らない種類は読み飛ばす（両方向）。** 後で種類を足しても、古いアプリ・古いファームウェアと組み合わせられるように。
7. **送れないときは、試し直すが、いつまでも続けない。** 送り終わりの知らせが来ないものは時間で見切る。送れない状態が 5 秒続いたらやめる（アプリの次の「開始」でまた始まる）。

## 3. 見分けるための値とレポートの記述

| 項目 | 値 | 移すとき |
| --- | --- | --- |
| usage page / usage | `0xFF4C` / `0x01`（ベンダー定義） | **変えない**（アプリはこれで見分ける） |
| レポート | 入力・出力とも **32 バイト**、**レポート ID なし**（WebHID では `reportId` 0） | 変えない |
| VID / PID | `0x1D50` / `0x615E`（ZMK の標準。ほかの ZMK キーボードとも同じ） | キーボードの値のまま |
| 製品名 | `LalapadGen2` | キーボードの名前。アプリは usage page と製品名で見分ける |

レポートの記述（HID report descriptor）。USB と Bluetooth で同じものを使う（25 バイト）:

```
06 4C FF   Usage Page (0xFF4C, ベンダー定義)
09 01      Usage (0x01)
A1 01      Collection (Application)
15 00        Logical Minimum (0)
26 FF 00     Logical Maximum (255)
75 08        Report Size (8)
95 20        Report Count (32)
09 01        Usage (0x01)
81 02        Input (Data, Var, Abs)      … キーボード → PC の 32 バイト
09 02        Usage (0x02)
91 02        Output (Data, Var, Abs)     … PC → キーボードの 32 バイト
C0         End Collection
```

## 4. レポートの形（共通）

- どのレポートも 32 バイト。使わない分は 0 で埋める。数値は**リトルエンディアン**。
- `[0]` 形式の版（今は `1`）、`[1]` 種類、`[2..]` 種類ごとの中身。
- キーボード → PC の種類は `0x01`〜`0x7F`、PC → キーボードの種類（命令）は `0x81`〜`0xFF`。
- キーボードは、形式の版が `1` でない命令、2 バイトより短い命令を捨てる。知らない種類の命令も捨てる（答えない）。
  命令は先頭 4 バイトだけを見る（`[2]`・`[3]` の引数まで）。
- アプリは、32 バイトより短いレポート、形式の版が違うレポートを読まない。知らない種類は読み飛ばす。

## 5. メッセージの一覧と中身

### 5.1 一覧

| 向き | 種類 | 名前 | 必須か |
| --- | --- | --- | --- |
| PC → キーボード | `0x81` | 開始・生存確認 | 必須 |
| PC → キーボード | `0x82` | 終了 | 必須 |
| PC → キーボード | `0x83` | 状態の問い合わせ | 必須 |
| PC → キーボード | `0x84` | 書き込み待ちの準備 | 拡張 |
| PC → キーボード | `0x85` | 書き込み待ちにする | 拡張 |
| PC → キーボード | `0x86` | レイヤーの見分けの番号の問い合わせ | 拡張 |
| キーボード → PC | `0x01` | キー（押した・離した） | 必須 |
| キーボード → PC | `0x02` | 状態 | 必須 |
| キーボード → PC | `0x03` | 押されているキーの一覧 | 必須 |
| キーボード → PC | `0x04` | レイヤー・修飾キー | 拡張（開始で頼まれたときだけ） |
| キーボード → PC | `0x05` | 書き込み待ちの答え | 拡張 |
| キーボード → PC | `0x06` | レイヤーの見分けの番号 | 拡張 |

拡張を作らないファームウェアは、その命令を無視し（答えない）、`0x02` の `[8]` のビットを 0 にする。`0x04` を作らないなら、開始の bit2 を無視する。

### 5.2 PC → キーボード

**`0x81` 開始・生存確認**

| 位置 | 中身 |
| --- | --- |
| 2 | 送ってほしい種類（ビット）。bit0 = キー（位置 0〜キーの位置の数−1）、bit1 = キー以外の位置（LaLapad Gen2 ではトラックパッドのタップ・ジェスチャー 52〜67）、bit2 = レイヤー（`0x04`）。ほかのビットは 0 にして無視する。2 バイト目がない（長さ 2）なら bit0 だけとみなす |

- 入力先からのものだけを受け付ける（[6.4](#64-入力先との照合)）。入力先でなければ、何もせず、生存確認の時間も数え直さない。
- 今送っていない、または送り道（USB／Bluetooth の接続）か種類が今と違う → **始め直し**（[6.3](#63-始める始め直す)）。
- 今と同じ送り道・同じ種類 → **生存確認だけ**（時間を数え直す。状態は送り直さない）。

**`0x82` 終了** — 中身なし。今送っている送り道からのものなら、送るのをやめる（[6.6](#66-やめる)）。ほかからのものは無視する。

**`0x83` 状態の問い合わせ** — 中身なし。今送っている送り道からのものなら、状態（`0x02`）、押されているキーの一覧（`0x03`）、
レイヤーを頼まれていればレイヤー（`0x04`）を送る。送っていないときは答えない（入力先でないことを確かめるのに使える）。

**`0x84` 書き込み待ちの準備・`0x85` 書き込み待ちにする**（拡張。UF2 のブートローダーに入れる）

| 位置 | 中身 |
| --- | --- |
| 2 | どちら（0 = 親機、1 = 子機） |

- 今送っている送り道からのもので、入力先の照合が済んでいて（[6.4](#64-入力先との照合)）、今も入力先であるときだけ受け付ける。それ以外は答えない。
- `[2]` が 0・1 以外なら答えない。
- うっかり入らないよう、**準備（`0x84`）の後 3 秒以内に、同じ送り先・同じ始め方（始め直していない）で、同じどちらへの実行（`0x85`）が来たときだけ**入る。
  準備は 1 回で使い切る（実行が来たら、成功でも失敗でも消す）。止める・始め直すと準備は使えなくなる。
- 答え（`0x05`）の結果:
  - 準備を受けたら 1（準備した）。
  - 実行で、準備がない・3 秒を過ぎた・どちらが違う・始め直した後なら 2。
  - 子機を指定したのに子機とつながっていなければ 3。
  - ブートローダーに入る手段がない（キーマップに `&bootloader` がない、子機を指定したが分割でない）なら 4。
  - すでに入ると決めていれば、入るまでどの命令にも 2。
  - 入ると決めたら 0 を答え、**0.5 秒後に**入る（答えが PC に届くよう努めるが、届いたかどうかには結びつけない）。
- 親機は自分で入る。子機には、親機から「子機の `&bootloader` を押した」ことにして分割の仕組みで伝える（子機のファームウェアは変えなくてよい）。
  子機に伝えた後、親機は次の命令（親機を書き込み待ちにするなど）を受け付けられる状態に戻る。
- アプリは、両方を書き込むときは**子機を先に**する（親機が先に入ると、子機に伝えられない）。

**`0x86` レイヤーの見分けの番号の問い合わせ**（拡張） — 中身なし。今送っている送り道からのものなら、`0x06` を先頭から送る。

### 5.3 キーボード → PC

**`0x01` キー**（1〜4 件まとめて）

| 位置 | 中身 |
| --- | --- |
| 2〜3 | 先頭の通し番号（u16） |
| 4 | 件数 n（1〜4） |
| 5 + 6×i | 位置番号（u8） |
| 6 + 6×i | 印: bit0 = 押した（1）／離した（0）、bit1 = 開始したときに押されたままだったキー（スナップショット） |
| 7 + 6×i 〜 10 + 6×i | 時刻（キーボードが起動してからのミリ秒、u32。キーの出来事の時刻。スナップショットは開始した時刻） |

- i 件目の通し番号は「先頭 + i」（65536 で割った余り）。
- 時刻はキーボードの時計。Bluetooth では数件まとめて届くので、打鍵の間隔は届いた時刻ではなくこの値で見る。

**`0x02` 状態**

| 位置 | 中身 |
| --- | --- |
| 2 | 子機との接続がある（1）／ない（0）。分割でなければ 0 |
| 3 | 今送っている種類（開始で受け付けたビット） |
| 4 | キーの位置の数（この番号より前がキー、ここからがキー以外の位置。LaLapad Gen2 は 52） |
| 5 | 位置の数の合計（LaLapad Gen2 は 68） |
| 6〜7 | 次に送るキーの通し番号（u16。送り待ちがあればその先頭、なければ次に振る番号） |
| 8 | できること: bit0 = `0x84`・`0x85` を受け付ける、bit1 = `0x86` に番号を答える（番号を持っているときだけ 1） |

- 送るとき: 始め直したとき、問い合わせのとき、子機とのつながりが変わったとき、送り終わらなかった状態を見切ったとき。

**`0x03` 押されているキーの一覧**

| 位置 | 中身 |
| --- | --- |
| 2〜3 | 通し番号（u16）。この番号より前のキーまでを反映した一覧 = 次に送るキーの番号 |
| 4 | 位置の数の合計 |
| 5〜 | 押されている位置のビット。位置 p は `[5 + p/8]` の bit `(p % 8)`（1 = 押されている） |

- 今送っている種類の位置だけを入れる（キー以外の位置を頼まれていなければ、それらは 0）。
- 送るとき: 始め直したとき、問い合わせのとき、送り待ちがあふれてキーを捨てたとき、送り終わらなかったキー・一覧を見切ったとき。
- **送り待ちのキーをすべて送り始めてから**、その時点の状態で作る（[6.5](#65-送る順番と送り方)）。

**`0x04` レイヤー・修飾キー**（拡張。開始の bit2 で頼まれたときだけ）

| 位置 | 中身 |
| --- | --- |
| 2〜5 | 有効なレイヤー（u32。bit L = レイヤー ID L が有効。いちばん下の既定のレイヤーと、条件付きレイヤーも含む） |
| 6 | レイヤーの数 |
| 7〜10 | このレポートを作った時刻（起動してからのミリ秒、u32） |
| 11 | 押している修飾キー（HID の修飾キーと同じ並び: bit0 左 Ctrl、bit1 左 Shift、bit2 左 Alt、bit3 左 GUI、bit4〜7 右の同じ順）。修飾キーそのもの（`&kp LSHIFT`、長押しの Shift、一度だけの Shift など）だけで、`LS(N1)` のようにキーに付いた修飾は含まない |
| 12 | 有効なレイヤーの件数 n（0〜19） |
| 13 〜 12 + n | 有効なレイヤーの ID を、ファームウェアがキーを探す順（いちばん上から、いちばん下の既定のレイヤーまで）に並べたもの。20 個以上有効なら上の 19 個 |

- レイヤー ID は、キーマップに書いた順番（0 から）。ZMK Studio でレイヤーの順番を入れ替えても ID は変わらない（上下は 13 以降の並びで分かる）。
- n = 0 は「順番を送れなかった」（古いファームウェア、または順番の表を書き換えている最中だった）。アプリはいちばん大きいビットを上とみなす。
- 送るとき: 始め直したとき、問い合わせのとき、レイヤーが変わったとき、修飾キーのキーが押された・離されたとき、修飾キーの見直しで変化を見つけたとき（[6.7](#67-レイヤー修飾キーの見張り)）、
  送り終わらなかったものを見切ったとき。**送るときの状態**で作る（何度変わっても、送るのは最後の 1 つ）。キー（`0x01`）より先に送る。

**`0x05` 書き込み待ちの答え**（拡張）

| 位置 | 中身 |
| --- | --- |
| 2 | どちら（命令の `[2]` と同じ） |
| 3 | 結果（0〜4。5.2 の `0x84`・`0x85` を参照） |

- 送り直さない（見切っても再送しない）。アプリは答えが来なくても、書き込み待ちのドライブが出たら入ったとみなす。

**`0x06` レイヤーの見分けの番号**（拡張）

| 位置 | 中身 |
| --- | --- |
| 2 | このレポートの先頭のレイヤー ID |
| 3 | レイヤーの数（番号を持っていなければ 0） |
| 4 | このレポートの件数 n（0〜27） |
| 5 〜 4 + n | レイヤー ID（先頭 + i）ごとの見分けの番号（1〜255） |

- 見分けの番号は、名前を変えても並べ替えても変わらない、レイヤーごとの番号（LaLapad Gen2 ではキーマップのラベル `layer_id_<番号>:`）。
  アプリはこれで、キーボードのレイヤー ID をキーマップのファイルのレイヤーに対応させる。
- 27 を超えるときは、続きを次のレポートで送る。番号を持っていなければ、レイヤーの数 0・件数 0 のレポートを 1 つ送る。
- 送り終わらなかったものを見切ったら、先頭から送り直す。送っている間に問い合わせ直されたら、先頭から送り直す。

## 6. キーボード側の動き（状態の移り変わり）

### 6.1 持っておく状態

| 状態 | 意味 |
| --- | --- |
| 送っているか、送り道（USB／Bluetooth の接続）、送る種類（ビット） | 開始で決まる |
| 最後に開始が届いた時刻 | 生存確認 |
| 押されている位置（位置ごとの真偽）、位置ごとに最後に受けた出来事の時刻 | 一覧・スナップショット・重なりの見分けに使う。**送っていない間も常に更新する** |
| 送り待ちのキー（輪状の待ち行列、64 件）と、次に振る通し番号（u16） | 通し番号は**起動したときに 0** から始め、終了・開始・始め直し・種類の変更では**戻さない**（キーを送り待ちに足すたびに 1 つ進む。捨てた分も進んだまま） |
| 「頼まれた回数」と「送り始めた回数」の組（状態・一覧・レイヤー・番号・書き込み待ちの答え） | 違えば送り待ち。真偽ではなく回数で持つ（送っている最中に頼まれ直しても落とさないため） |
| 送っている最中のレポート（あるか、番号、種類、送り道） | 1 つずつ送るため |
| 入力先が変わったの知らせの回数と、照合した回数、照合の前に入力先が実際に変わったか | [6.4](#64-入力先との照合) |
| 送れない状態が続き始めた時刻 | 5 秒で諦める |
| 始め方の世代（始め直す・やめるたびに 1 つ進む） | 書き込み待ちの準備を結びつける |

複数のスレッド（キーの出来事、PC からの命令、送り終わりの知らせ、接続の変化）から触るので、短い lock（spinlock など）で守る。
送り道を呼ぶ（送る）ときは lock の外で呼ぶ。

### 6.2 キーの出来事を受けたとき

1. 位置番号が範囲外なら何もしない。
2. **押した状態が今と同じ出来事、またはその位置で前に受けた出来事より時刻が古い出来事は、捨てる**（ZMK の combos は、判定のために預かったキーを元の時刻のまま
   出し直すので、同じ「押した」が 2 回届いたり、「離した」の後に古い「押した」が届いたりする）。
3. 押されている位置と、その位置の時刻を更新する。
4. 送っていて、その位置の種類（キー／キー以外）を頼まれていれば、送り待ちに足す（通し番号を振る。印は押したなら bit0）。足したら送る処理を起こす。
5. 送り待ちが満杯（64 件）なら、いちばん古いものを捨ててから足し、押されているキーの一覧を頼む（捨てた中に「離した」があると、アプリで押されたままに見えるため）。
   **通し番号は捨てた分も進んだまま**（アプリには番号の飛びとして見える）。
6. レイヤーを頼まれていれば、修飾キーの見張りを始める（[6.7](#67-レイヤー修飾キーの見張り)）。

キーの出来事は止めない・遅らせない（見るだけ）。

### 6.3 始める・始め直す

開始（`0x81`）が入力先から届き、始め直しに当たるとき（今送っていない、送り道か種類が違う）:

1. 今の送信をやめる（送り待ちのキーと、頼まれていた状態・一覧などをすべて捨てる。世代を進める）。
   送っている最中のレポートが別の送り道のものなら、その送り終わりは待たない（後から届いても番号が違うので無視される）。同じ送り道なら、ふつうに待つ。
2. 送り道・種類を覚え、送っている状態にする。
3. 状態（`0x02`）を頼む。
4. その時点で押されている位置のうち頼まれた種類のものを、**1 件ずつ送り待ちに足す**（印 = 押した＋スナップショット、時刻 = 今）。
5. 押されているキーの一覧（`0x03`）を頼む。
6. レイヤーを頼まれていれば、レイヤー（`0x04`）を頼む。
7. 生存確認の時間（6 秒）を数え始め、送る処理を起こす。

同じ送り道・同じ種類の開始は、生存確認の時間を数え直すだけ。生存確認の時間が切れたら、やめる。

### 6.4 入力先との照合

「入力先」= ファームウェアが今キーの入力を送っている先。ZMK では `zmk_endpoints_selected()`。

- USB から届いた命令: 入力先が USB なら入力先。
- Bluetooth から届いた命令: 入力先が Bluetooth で、選んでいるプロファイルがつながっていて、その接続が命令の届いた接続と同じなら入力先
  （ほかのプロファイルでつながったままの PC は入力先ではない。どこにもつながっていないとき ZMK は Bluetooth を選んだことにするので、つながっているかも確かめる）。

入力先が変わったの知らせ（ZMK では `zmk_endpoint_changed`、選んでいるプロファイルの接続が変わったときの `zmk_ble_active_profile_changed`）を受けたら:

1. 知らせの回数を 1 つ進め、送る処理を止める（**照合が済むまで、何も送らない**。入力先が変わった後に押したキー＝別の PC で打ったキーを、前の PC に送らないため。
   その間のキーは送り待ちにためておく）。`zmk_endpoint_changed` なら「実際に変わった」印も付ける。
2. 専用のスレッドで照合する: 送っていて、「実際に変わった」印がなく、今の送り道が入力先なら続ける。そうでなければやめる
   （A → B → A と切り替える間に B で打ったキーを A に送らないよう、実際に変わっていたら、照合の時点で A に戻っていてもやめる）。
3. 照合した回数を知らせの回数に合わせる。続けるなら、ためていたキーを送る。
4. 照合している間に次の知らせが来たら、照合待ちのまま次の照合で決める。

やめたことはアプリに知らせない（届かなくなるだけ）。アプリは開始を送り続けているので、入力先がその PC に戻れば、次の開始で始め直しとして、状態と押されているキーから届く。
入力先が変わった直後の開始で始めたときは、その開始の照合が最新なら「実際に変わった」印を消す（並んでいる照合が、始めたばかりの送信をやめないように）。
起動したときにも 1 回照合する（照合の仕組みが動き出す前に届いた知らせの分）。

### 6.5 送る順番と送り方

送る処理（専用のスレッド）は、送っていて、送っている最中のレポートがなく、照合が済んでいるときだけ、次の 1 つを作って送る。順番:

1. 状態（`0x02`）
2. 書き込み待ちの答え（`0x05`）
3. レイヤー（`0x04`。頼まれていなければ、頼まれていた分を捨てる）
4. レイヤーの見分けの番号（`0x06`。数回に分けて送る）
5. 送り待ちのキー（`0x01`。先頭から最大 4 件）
6. 押されているキーの一覧（`0x03`。送り待ちのキーがなくなってから）

- 送るたびに番号（u32、1 つずつ進める）を付け、送っている最中として覚える。送り道は、送り終わったらその番号で知らせる。
  知らせの番号が送っている最中のものと違えば無視する（見切った後や送り道を変えた後に、遅れて届いた知らせと取り違えないため）。
- 送り始められたら、その種類の「送り始めた回数」を、作ったときの「頼まれた回数」に合わせる（キーなら送った件数を送り待ちから外す。送っている間にあふれて先頭が進んでいたら、その分は数えない）。
- 送り道の答え:
  - 0 = 送り始めた。送り終わりの知らせを待つ。来なければ **USB は 0.5 秒、Bluetooth は 3 秒で見切る**。
    見切ったら、状態は頼み直す、レイヤーは（今も頼まれていれば）頼み直す、番号は先頭から頼み直す、書き込み待ちの答えは送り直さない、キー・一覧なら一覧を頼む。そして次へ進む。
  - 「今は送れない」（-EAGAIN）なら 5 ms 後に、「しばらく送れない」（-EBUSY）なら 100 ms 後に試し直す。送れない状態が**続けて 5 秒**になったら、やめる。
  - そのほかの失敗なら、やめる。
- 送り道が切れた（USB を抜いた、Bluetooth が切れた）ら: その送り道で送っていればやめる。その送り道で送っている最中のレポートがあれば、待つのをやめる。
- 送るものが増えたときは、試し直しを待っている最中なら、その時刻を早めない（キーを押すたびに試し直しが早まって、Bluetooth の暗号化を頼み直したりしないように）。

### 6.6 やめる

やめるのは: 終了（`0x82`）、生存確認の時間切れ（6 秒）、入力先でなくなった、送り道が切れた、送れない状態が 5 秒続いた、送り道が送れないと答えた。
やめたら、送り待ちと頼まれていたものをすべて捨て、世代を進める（書き込み待ちの準備も使えなくなる）。押されている位置の記録は捨てない（常に更新している）。
アプリには知らせない。

### 6.7 レイヤー・修飾キーの見張り

レイヤーを頼まれている間だけ:

- レイヤーが変わったとき、修飾キーのキーコード（HID のキーボードのページの `0xE0`〜`0xE7`）が押された・離されたときに、レイヤー（`0x04`）を頼む。
- それに加えて、**キーを押している間と、修飾キーが残っている間は、20 ms ごとに修飾キーを読み**、前に送ったものと違えばレイヤーを頼む
  （ZMK の hold-tap は、判定の間に預かった修飾キーの出来事を、自分より後ろの仕組みにだけ出し直すので、知らせが届かないことがあるため）。
- 修飾キーは「修飾キーそのものを押しているもの」（ZMK では `zmk_hid_get_explicit_mods()`）。
- 順番の表を読むとき（13 以降）、表全体に同じ ID が 2 回出たら書き換えの最中とみなし、件数 0 で送って、**送り終わってから 50 ms 後に**送り直す（続けて 5 回まで。その後は、次にレイヤーが変わったときに送る）。

### 6.8 子機とのつながり

分割キーボードでは、子機との接続ができた・切れたときに状態（`0x02`）を頼む（`[2]` の値は送るときに数える）。
子機が切れたときの子機のキーの「離した」は、ファームウェアがふつうのキーの出来事として出すので、そのまま送られる。
ファームウェアが「離した」を出さない位置（LaLapad Gen2 では子機のトラックパッドの位置）は、別の仕組みで離してから送る（[lalapad/src/position_relay.c](../lalapad/src/position_relay.c)）。

## 7. 送り道（USB・Bluetooth）の作り方

本体と送り道の取り決め（[key_stream.h](../lalapad/src/key_stream.h)）:

| 向き | 関数 | 決まり |
| --- | --- | --- |
| 送り道 → 本体 | `key_stream_received(送り道, 接続, データ, 長さ)` | PC から届いた命令。どのスレッドからでもよい（本体は写して、専用のスレッドで処理する）。どの PC からのものでも渡してよい（入力先かは本体が確かめる） |
| 送り道 → 本体 | `key_stream_sent(番号)` | 送り終わった。届かないこともある（本体は時間で見切る） |
| 送り道 → 本体 | `key_stream_transport_lost(送り道, 接続)` | 送り道が切れた |
| 本体 → 送り道 | `key_stream_usb_send(レポート, 番号)` / `key_stream_ble_send(接続, レポート, 番号)` | 32 バイトを 1 つ送り始める。戻るまでに写す。0 = 送り始めた、-EAGAIN = 今は送れない、-EBUSY = しばらく送れない、そのほか = 送れない |

### 7.1 USB

- ふだんのキーボードの HID の口とは別に、HID の口（インターフェース）を**もう 1 つ**増やす（ZMK / Zephyr では `CONFIG_USB_HID_DEVICE_COUNT=2` で `HID_1` を使う）。
- 入力レポートは割り込み IN エンドポイントで送る。**PC からの命令は、出力レポート（SET_REPORT、制御転送）で受け取る**（割り込み OUT エンドポイントは付けない。
  Zephyr では付けると、ZMK のキーボードの口にも OUT が付き、キーボードの LED などの出力レポートが届かなくなる）。SET_REPORT のうち、レポートの種類が出力でないものは断る。GET_REPORT は受け付けない。
- ブートプロトコルは使わない（使うと、すべての HID の口がブート用キーボードとして名乗り、この口も PC からキーボードに見える）。
- 送り終わりの知らせ（IN の転送が終わった）で `key_stream_sent` を呼ぶ。知らせからはどの転送が終わったか分からないので、最後に送った番号を渡す。
- USB の機器は、送り終わるまで渡したバッファから直接読む（エンドポイントが 16 バイトなら 2 回に分ける）。**バッファは 2 つを交互に使い、最後に受け付けられた転送のバッファは書き換えない**
  （本体は見切った後に次を送ってくることがあるため）。前の転送が終わっていないと断られる（-EAGAIN・-EBUSY → 本体には -EBUSY を返す）。
- PC がサスペンドしている間は -EBUSY を返す。HID として使えない（つながっていない）間は -ENOTCONN。
- USB が HID として使えなくなったら（抜いたなど）、`key_stream_transport_lost(USB)`。

### 7.2 Bluetooth（HID over GATT）

- ふだんのキーボードの HID のサービスとは別に、**HID のサービスをもう 1 つ**増やす。属性の並び:

  | 属性 | 性質 | 権限 |
  | --- | --- | --- |
  | Primary Service: HID Service（0x1812） | | |
  | HID Information（0x2A4A）: bcdHID 0x0000、国コード 0、flags = NormallyConnectable（bit1） | Read | 暗号化なしで読める |
  | Report Map（0x2A4B）: [3](#3-見分けるための値とレポートの記述) のレポートの記述 | Read | 暗号化が要る |
  | Report（0x2A4D）: 入力 | Read・Notify（読まれたら 32 バイトの 0） | 暗号化が要る |
  | 　CCC（通知の設定） | | 読み書きとも暗号化が要る |
  | 　Report Reference（0x2908）: ID 0、種類 1（入力） | | 暗号化が要る |
  | Report（0x2A4D）: 出力 | Read・Write・Write Without Response（読まれたら 32 バイトの 0、書かれたら命令） | 読み書きとも暗号化が要る |
  | 　Report Reference（0x2908）: ID 0、種類 2（出力） | | 暗号化が要る |
  | HID Control Point（0x2A4C） | Write Without Response（1 バイトを受け取るだけ） | 暗号化なしで書ける |

- 権限は、ふだんのキーボードの HID のサービスに合わせる（Windows がこのサービスを HID として扱うため）。命令の書き込みは offset 0 だけを受け付ける。
- 送るのは入力レポートの通知。送り終わりの知らせ（通知を送った）の中で、その送信の番号を `key_stream_sent` に渡す。
- 送る前に確かめる: 接続がない・通知を購読していない → -ENOTCONN。**ATT MTU が 35 未満**（32 バイト＋頭 3 バイト）→ -EBUSY。
  暗号化されていない（通知が -EPERM）→ 暗号化を頼んで -EBUSY。Bluetooth の準備ができていない（-EAGAIN）→ -EBUSY。バッファが足りない（-ENOMEM・-ENOBUFS）→ -EAGAIN。
- 接続が切れたら `key_stream_transport_lost(BLE, 接続)`。
- 接続は、送り道を見分けるためにポインタで比べる。命令や送り先として持つ間は参照を持ち（`bt_conn_ref`）、手放すときに `bt_conn_unref`。
- 書き込んだ後、Windows が前の HID の情報を覚えていると、増えたサービスが見えない。キーボードを削除してペアリングし直す。

## 8. アプリ側の動き

### 8.1 つなぐ・続ける・切る

1. usage page `0xFF4C`・usage `0x01`（と製品名）で機器を探して開く。WebHID なら
   `navigator.hid.requestDevice({ filters: [{ vendorId, productId, usagePage: 0xFF4C, usage: 0x01 }] })`。
   - WebHID: 送るときは `device.sendReport(0, 32 バイト)`（レポート ID 0）。届くものは `inputreport` の `data`（32 バイト。レポート ID は含まない）。
   - hidapi: レポート ID を使わない機器なので、`hid_write()` には**先頭にレポート ID の `0x00` を付けた 33 バイト**を渡す（通信で送られるのは後ろの 32 バイト）。
     `hid_read()` で届くのは 32 バイト（OS によってはレポート ID の 1 バイトが付かないことを前提に、長さで確かめる）。
2. 通し番号の記録を空にする（前の値を引き継がない）。押されている表示を空にする。
3. 開始（`0x81`、`[2]` = 欲しい種類）を送り、続けて**問い合わせ（`0x83`）も送る**（閉じてから 6 秒たつ前に開き直すと、キーボードはまだ前の開始で送っていて、
   今の開始が生存確認として扱われ、状態と一覧が届かないため）。
4. **2 秒ごとに開始を送り続ける**（届かなくても送り続ける。入力先がこの PC に戻ったときに、それで始め直されるため）。
5. 開いてから 3 秒ほど状態（`0x02`）が届かなければ、「キーボードの入力先がこの PC ではない」と知らせてよい（入力先でない PC には何も答えないため）。
6. 閉じるときは終了（`0x82`）を送ってから閉じる。機器が外れたときは送らない。
7. 種類を変えるときは、新しい種類の開始を送る（始め直しになり、状態と押されているキーから届く。まだ送っていなかったキーは捨てられ、番号が飛んで見える）。

### 8.2 受け取ったとき

- 32 バイトより短いもの、`[0]` が 1 でないものは読まない。知らない種類は読み飛ばす。
- **通し番号の確かめ方**（キー・状態・一覧で共通）:

  ```
  expected = null                        // 開いたとき・つなぎ直したとき
  function check(seq):                   // 届いた番号（キーなら先頭、状態なら [6..7]、一覧なら [2..3]）
      if expected == null or seq == expected: return
      gap = (seq - expected) & 0xFFFF
      if gap >= 0x8000: return           // 戻った（キーボードの再起動など）。取りこぼしとは数えずに数え直す
      lost += gap                        // その分を取りこぼした
  キー（0x01）: check(先頭); 1 件ごとに処理; expected = (先頭 + n) & 0xFFFF
  状態（0x02）: check([6..7]); expected = [6..7]
  一覧（0x03）: check([2..3]); expected = [2..3]
  ```

  戻ったかどうかは目安（再起動の後の番号が、たまたま進んで見えることもある）。
- キー: 印の bit0 で押した・離したを反映する。bit1（スナップショット）は「開始したときに押されたままだった」キー。一覧（`0x03`）でも同じことが分かるので、どちらで受けてもよい。
- 一覧: 押されている状態を**丸ごと置き換える**（0 の位置は離されている）。
- 状態: `[4]` から先の位置はキー以外。`[2]` で子機のつながりを出せる（1 でも、つながった直後は子機のキーがまだ届かないことがある）。
- レイヤー: [5.3](#53-キーボード--pc) のとおり。上下は 13 以降、件数 0 ならいちばん大きいビットを上。有効なレイヤーが変わらないまま順番だけ入れ替わったときは届かないので、要るなら問い合わせる。
- 子機が切れたときは、状態（切れた）と、子機で押されていたキーの「離した」が届く（どちらが先かは決まっていない）。

## 9. ほかのキーボード・ファームウェアに移すとき

### 9.1 キーボードごとに変わるもの

| もの | LaLapad Gen2 | 移すとき |
| --- | --- | --- |
| 位置の数の合計 | 68 | そのキーボードのキーマップの位置の数。**255 以下**（位置は 1 バイト）、かつ一覧に入るよう **216 以下**（5 + ⌈N/8⌉ ≤ 32） |
| キーの位置の数（キーとキー以外の境目） | 52（52〜67 はトラックパッドのタップ・ジェスチャー） | キー以外の位置がなければ合計と同じにし、開始の bit1 は使わない |
| レイヤーの数 | 14 | 32 以下（u32 のビット） |
| VID / PID・製品名 | ZMK の標準・`LalapadGen2` | そのキーボードの値 |
| 位置番号の並び・実際の配置 | README の「キーの位置番号」、[key-stream-layout.json](key-stream-layout.json) | アプリに渡す資料として作る |
| 拡張（`0x04`〜`0x06`、`0x84`〜`0x86`） | あり | 要らなければ作らない（`0x02` の `[8]` を 0、開始の bit2 を無視） |

**変えないもの**: usage page・usage、32 バイト・レポート ID なし、形式の版、種類の番号と中身の並び、生存確認（2 秒・6 秒）の決まり、入力先にだけ送る決まり、通し番号と一覧の決まり。
これらを変えると、同じアプリが使えなくなる。

### 9.2 ZMK のキーボードに移す

1. `lalapad/src/key_stream.c`・`key_stream_usb.c`・`key_stream_ble.c`・`key_stream.h` を写す。依存しているもの:
   - `tp_positions.h` の `POS_TP_FIRST`（キーの位置の数）→ そのキーボードの値に置き換える（キー以外の位置がなければ `ZMK_KEYMAP_LEN`）。
   - `split_link.h`（子機との接続を見分ける `is_split_link`、`WATCH_SPLIT_LINK`）→ 分割でなければ、子機とのつながりの部分（[6.8](#68-子機とのつながり)）を外す。
   - `layer_ids.h`（`0x86` の番号）→ 要らなければ `CONFIG_ZMK_LAYER_IDS` を作らず、その部分は 0 になる。
2. Kconfig: `ZMK_KEY_STREAM`（親機だけ。`ZMK_USB || ZMK_BLE` に依存）、`ZMK_KEY_STREAM_USB`（既定 y、`ZMK_USB` に依存）、`ZMK_KEY_STREAM_BLE`（既定 y、`ZMK_BLE` に依存）。
   CMake でそれぞれのファイルを足す。
3. 親機の `.conf` に `CONFIG_ZMK_KEY_STREAM=y` と `CONFIG_USB_HID_DEVICE_COUNT=2`。`CONFIG_ENABLE_HID_INT_OUT_EP` と `CONFIG_ZMK_USB_BOOT` は使えない（ビルドで止める）。
4. 専用のスレッド: スタック 1536 バイト、優先度 6 のワークキュー。

### 9.3 ZMK でないファームウェア（QMK など）に移す

- 仕組みの核（[6](#6-キーボード側の動き状態の移り変わり)）は、OS の機能に依らない。「キーの出来事を見るだけの口」「1 つずつ送る仕組み（送り終わりを待つ、または送れたら次）」
  「PC からのレポートを受け取る口」「入力先を知る手段」「起動からのミリ秒の時計」があれば作れる。スレッドがなければ、メインループの中で 1 つずつ送る形にしてよい（キーの処理を止めないこと）。
- usage page を **`0xFF4C`・usage `0x01` に合わせる**。QMK の raw HID は既定で usage page `0xFF60`・usage `0x61`（`RAW_USAGE_PAGE`・`RAW_USAGE_ID` で変えられる）。
  レポートの大きさ（アプリとやり取りする 1 回分）は 32 バイトで、この仕様と同じ。ただし USB のエンドポイントの大きさとは別のもので、
  LUFA・ChibiOS ではエンドポイントも 32 バイト（`RAW_EPSIZE`）だが、V-USB ではエンドポイントが 8 バイト（`RAW_EPSIZE`）で、32 バイト（`RAW_BUFFER_SIZE`）を分けて送る。
  どちらでも、アプリから見たレポートは 32 バイト。
- QMK の raw HID は OUT エンドポイントで受け取るが、アプリから見れば同じ出力レポートなので、アプリは変えなくてよい。
- 位置番号は、そのファームウェアのキーマップの並びの番号にする（QMK なら、行・列から作るキーマップの順番）。
- 有線だけなら入力先は 1 つ（USB）。無線で接続先を切り替えられるなら、[6.4](#64-入力先との照合) の決まり（入力先からの開始だけ・切り替えたらやめる）を守る。
- 時刻は起動からのミリ秒（u32。約 49 日で 0 に戻る）。

## 11. 確かめる項目

移したら、最低限これを確かめる（[docs/tools/key-stream-viewer.html](tools/key-stream-viewer.html) を Chrome か Edge で開けば、1〜6 は見られる）。

1. USB で開始すると、状態 → （押していれば）スナップショットのキー → 一覧の順に届く。キーを押す・離すと `0x01` が届き、通し番号が飛ばない。
2. アプリを閉じて（終了を送らずに）6 秒たつと、送られなくなる。開き直すと、問い合わせで状態と一覧が届く。
3. Bluetooth でも 1 と同じ。Windows でサービスが見えなければ、ペアリングし直す。
4. USB と Bluetooth の両方につないで入力先を切り替えると、入力先でない側には何も届かず、戻すと 2 秒ほどで状態から届き直す。Bluetooth のプロファイルを切り替えても同じ。
5. 速く打って送り待ちをあふれさせると（Bluetooth で多くのキーを同時に押し続けるなど）、番号が飛び、その後に一覧が届いて押されている表示が正しく直る。
6. 分割なら、子機を切ると状態（切れた）と子機のキーの「離した」が届く。
7. 拡張を作ったなら: レイヤーを変える・Shift を押すと `0x04` が届く。`0x84` の後 3 秒以内に `0x85` で書き込み待ちのドライブが出る（3 秒を過ぎると結果 2）。`0x86` に `0x06` が返る。
8. ふだんの入力（USB・Bluetooth）が、送っている間も遅れたり抜けたりしない。

## 12. わかっている制約

- VID/PID はほかの ZMK キーボードと同じなので、アプリは usage page と製品名も合わせて見分ける。
- アプリからは、届かない理由（入力先でない／キーを打っていない）を、届くものだけでは区別できない（問い合わせて答えが来るかで見る）。
- 入力先が変わってやめたことは知らせない。止まっている間のキーは届かない（戻ったときの一覧で直る）。
- 書き込み待ちの 2 段階の命令は誤操作を防ぐためのもので、相手のアプリを確かめるものではない（入力先の PC でこの HID を開けるアプリなら送れる）。
- Bluetooth は ATT MTU 35 以上・暗号化した接続が要る（Windows はふつう満たす）。
- `0x04` はキーより先に送るので、レイヤーを変えたキーより先に届くことがある。続けて変わったときは最後の状態だけが届く。
